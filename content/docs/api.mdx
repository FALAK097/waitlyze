title: Signup API

Use this endpoint when you collect emails on your own backend and want Waitlyze to own verification, referrals, and storage. Browsers should use the [hosted page or embed](/docs/embed) instead — never expose an API key client-side.

## Create an API key first

Go to Settings → Integrations → API keys, choose a waitlist, name the key, and set expiry. Copy the secret before closing: only its hash is stored. See [API keys](/docs/api-keys).

<Callout type="warn" title="Keep keys on your server">
A key grants signup-write access to one waitlist. Store it in a server environment variable such as `WAITLYZE_API_KEY`. Never put it in a browser bundle or public repository.
</Callout>

## Create a signup

`POST /api/waitlist` accepts JSON. Authentication uses the `apiKey` body field. This endpoint does **not** use a Bearer header.

<Tabs items={['Node.js', 'Python', 'cURL']}>
<Tab value="Node.js">
```js title="Server-side JavaScript"
const response = await fetch("https://waitlyze.falakgala.dev/api/waitlist", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    apiKey: process.env.WAITLYZE_API_KEY,
    waitlistId: "YOUR_WAITLIST_ID",
    email: "person@example.com",
    // referralCode: "OPTIONAL_REFERRAL_CODE"
  })
});
const result = await response.json();
if (!response.ok) throw new Error(result.error || "Signup failed");
```
</Tab>
<Tab value="Python">
```python title="Python · standard library"
import json
import os
from urllib.request import Request, urlopen
from urllib.error import HTTPError

request = Request(
    "https://waitlyze.falakgala.dev/api/waitlist",
    data=json.dumps({
        "apiKey": os.environ["WAITLYZE_API_KEY"],
        "waitlistId": "YOUR_WAITLIST_ID",
        "email": "person@example.com",
    }).encode("utf-8"),
    headers={"Content-Type": "application/json"},
    method="POST",
)
try:
    with urlopen(request, timeout=15) as response:
        result = json.load(response)
except HTTPError as error:
    result = json.load(error)
    raise RuntimeError(result.get("error", "Signup failed")) from error
```
</Tab>

## Handle responses

```json title="Success response"
{
  "success": true,
  "message": "Successfully joined the waitlist!",
  "data": {
    "rank": 9,
    "position": 9,
    "referral_code": "7f3a…",
    "referral_link": "https://waitlyze.falakgala.dev/w/your-slug?r=7f3a…",
    "verified": false
  }
}
```

`position` is the canonical queue position (`rank` is its legacy alias). `referral_code` is this signup's personal code and `referral_link` is the ready-to-share URL — render them in your confirmation UI when [referral sharing](/docs/referrals) is on. Both are `null`/`""` when sharing is disabled or the waitlist has no public slug. New signups start `verified: false` until they click the 24-hour confirmation link.

Duplicate emails return `409` **with the existing position**, so a retry never loses state:

```json title="Duplicate response (409)"
{
  "success": false,
  "error": "Email already registered for this waitlist",
  "data": { "position": 9, "referral_code": "7f3a…", "referral_link": "https://…" }
}
```

| Status | Meaning | Fix |
| --- | --- | --- |
| `400` | Missing or invalid input | Validate email, IDs, and JSON shape. |
| `401` | Bad key, expiry, or wrong linked waitlist | Check [API keys](/docs/api-keys) and `waitlistId`. |
| `409` | Duplicate email, key reuse, or not accepting signups | Read `data.position` for duplicates; mint a new `Idempotency-Key` on reuse; distinguish state reasons. |
| `404` | Status lookup found no signup | The email never joined this waitlist (lookup only). |
| `429` | Rate limited | Wait for `Retry-After`; back off, do not loop. |
| `503` | Rate-limit service unavailable | Retry after the provided interval. |
| `500` | Temporary server failure | Retry with exponential backoff. |

New API signups follow the same [verification flow](/docs/signup-flow): they receive a 24-hour confirmation link and stay unverified until they click it.

<Callout title="Dashboard routes need a session, not a signup key">
`/api/v1/api-keys` and `/api/v1/waitlists` are browser-session routes. A `waitlist:write` signup key cannot manage keys, list subscribers, or access them.
</Callout>

## Retry safely with Idempotency-Key

Network failures leave you unsure whether a signup landed. Send a client-generated `Idempotency-Key` header (1–128 chars: `A-Z a-z 0-9 _ -`) and retry with the **same** key and body:

```bash title="Idempotent signup"
curl --request POST 'https://waitlyze.falakgala.dev/api/waitlist' \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: 01J9Z8QK7M5N3P2R4T6V8X0Z2C4' \
  --data '{ "apiKey": "YOUR_SERVER_SIDE_API_KEY", "waitlistId": "YOUR_WAITLIST_ID", "email": "person@example.com" }'
```

- Replays return the original signup with `"idempotentReplay": true` in `data` — no duplicate is created.
- Reusing a key with a **different** email returns `409` (`Idempotency-Key was already used…`). Mint a fresh key per distinct signup.
- The key is also accepted alongside `x-api-key` / Bearer auth, keeping secrets out of the JSON body if you prefer.

## Look up a signup's status

`GET /api/waitlist?waitlistId=…&email=…` answers “where am I?” for custom frontends without consuming signup intake budget. The key travels in headers only — never in the query string:

```bash title="Status lookup"
curl 'https://waitlyze.falakgala.dev/api/waitlist?waitlistId=YOUR_WAITLIST_ID&email=person%40example.com' \
  --header 'X-Api-Key: YOUR_SERVER_SIDE_API_KEY'
```

```json title="Status response"
{ "success": true, "data": { "position": 9, "referral_code": "7f3a…", "referral_link": "https://…", "verified": true } }
```

Unknown emails return `404`. Responses are `private, no-store` — do not cache them in a CDN.

## Rate limits

Two budgets protect intake; both surface `Retry-After` on `429`/`503`:

- **Shared intake budget** — per campaign, client, and recipient windows (see [Troubleshooting](/docs/troubleshooting)).
- **Per-key daily budget** (5,000 signups + lookups per key per day). Every `POST`/`GET` response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (Unix seconds). Graph them per key to spot a noisy integration before it caps.
