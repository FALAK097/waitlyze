Resend gives Waitlyze a verified sender for verification, broadcast, and automation mail. Without it, Waitlyze falls back to the deployment sender.

## Connect your sender

<Steps>
<Step>
### Verify your domain in Resend
In the Resend dashboard, add and verify your sending domain, then create a **sending-only** API key. See [Resend domain setup](https://resend.com/docs/dashboard/domains/introduction).
</Step>
<Step>
### Connect in Waitlyze
Go to Settings → Integrations → **Resend → Connect**. This needs owner/admin permission. Enter the key and a sender email on your verified domain, then **Save**. The secret is encrypted and never returned to the browser — enter a replacement to change it.
</Step>
<Step>
### Save and test to activate
Send a test email. Tests go to your Waitlyze account email. The connection becomes **Active** only when the test succeeds; until then the deployment sender is used.
</Step>
</Steps>

## If a test fails

- Confirm the key is sending-only with send permission, not a full-access or expired key.
- Confirm the sender address domain matches a verified Resend domain exactly.
- Correct the details, save, and test again.
- Check [Email tools](/docs/email) delivery health for dispatcher versus sender errors.

Disconnecting falls back to the deployment sender immediately.

## Per-waitlist sender identity (planned)

Today one workspace shares one sender: every waitlist's verification, broadcast, and automation mail uses the workspace connection above. Per-waitlist sender identity — each waitlist with its own verified domain and sending-only key, falling back to the workspace sender — needs a data migration plus per-waitlist connect/test UI, so it is documented here as the contract rather than shipped half-built:

- Resolution order will be waitlist sender → workspace sender → deployment default.
- Connecting a waitlist sender will follow the same save-and-test-to-activate flow (status stays on the deployment sender until a test succeeds).
- Until then, send multi-brand waitlists from separate workspaces if sender separation matters.

## Bounces, complaints, and suppression

Signed Resend provider events update workspace suppression with recipient evidence. Bounced or complained addresses are excluded from future broadcasts and automations, including early webhook races where the complaint arrives before the send completes. This is automatic — you do not manage the suppression list by hand.
