# Waitlyze: Neon Postgres → Cloudflare D1?

Researched **November 11, 2026**. **Recommendation: do not migrate to D1 to address first-page latency or 1,000 daily users.** D1 can likely accommodate that _daily_ audience, but traffic distribution, rows scanned, write bursts, and query duration—not daily users—determine capacity. Production health checks showed 88–1,643 ms for a simple database round trip, but authenticated page traces and a load profile are still missing, so neither a D1 speedup nor a Neon capacity limit is established. Preserve Postgres; instrument the first slow request and evaluate Neon's paid always-on compute and, only if connection/network time dominates, a cache-disabled Hyperdrive experiment. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/); [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero); [Hyperdrive architecture](https://developers.cloudflare.com/hyperdrive/concepts/how-hyperdrive-works/).

## Live Neon CLI checks (November 11, 2026)

Read-only `neon projects list`, `neon postgres computes list`, and `neon operations list` confirmed a Free plan, a 0.25 CU primary in `aws-ap-southeast-1`, and 17 starts / 16 suspends on the main branch since November 10. Both direct and `--pooled` CLI connections completed `SELECT 1`; `EXPLAIN (ANALYZE) SELECT 1` reported 0.005 ms execution time. These checks support a wake/connection-path hypothesis for the intermittent health latency; they do not measure the Worker connection path or prove a particular bottleneck. [Neon CLI Postgres](https://neon.com/docs/cli/postgres); [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero).

## What this app actually does

- Public `/` (`src/app/page.jsx`) reads local templates/posts and performs no Prisma query; D1 would not fix that route's initial server response. The authenticated `/waitlists` first render _does_ resolve Better Auth session and workspace (`src/lib/workspaces/current.js`, `src/lib/auth.js`, `src/app/(app)/layout.jsx`), fetch entitlements, then count/list waitlists with relation counts (`src/app/(app)/waitlists/page.jsx`). `src/lib/workspaces/current.js` already logs session/workspace calls taking ≥500 ms. The app's OpenNext Worker routes to Next.js (`cloudflare-worker.js`), and `wrangler.jsonc` targets `aws:ap-southeast-1`; the Neon CLI confirms Waitlyze’s primary compute is also in `aws-ap-southeast-1`. Authenticated request traces remain unavailable.
- `prisma/schema.prisma` has **40 models**, `provider = "postgresql"`, Cloudflare Prisma runtime, enums, JSON, four `String[]` columns, and `@db.Timestamptz(3)` columns; there are **31** Postgres migration files. `src/lib/prisma.js` uses `PrismaNeon` with `@neondatabase/serverless`, `max: 1`, and rewrites Neon hostnames to `-pooler`; `src/lib/auth.js` uses Better Auth's Prisma adapter configured for PostgreSQL. `workers/outbox-dispatch/src/index.js` invokes the application's internal outbox endpoint, which also depends on the same database. These paths would all need regression coverage in a migration.
- At least **29 source files** call `$queryRaw`/`$executeRaw`; examples include Postgres `ILIKE`, `::bigint`, `ANY(...::text[])`, JSONB operators, `FOR UPDATE` in signup/billing/automation flows, advisory transaction locks in `src/lib/emails/cloudflare-usage.mjs` and API-key linking, and `FOR UPDATE SKIP LOCKED` in `src/lib/security/public-rate-limit.mjs`. Existing migrations use `CREATE TYPE`, `ALTER TYPE`, JSONB, `TEXT[]`, and Postgres-specific casts (`prisma/migrations/20261011000000_campaign_product_revamp/migration.sql`). This is a dialect and concurrency redesign, not a connection-string swap. [D1 SQL dialect](https://developers.cloudflare.com/d1/sql-api/sql-statements/); [Prisma scalar-list support](https://www.prisma.io/docs/orm/v6/reference/prisma-schema-reference#scalar-lists).

## Recommended path

1. Measure cold-after-idle and warm p50/p95 for public `/`, login/session, first authenticated `/waitlists`, and signup/write flows. Separate Worker/Next render, Neon wake/connection, session/workspace, and SQL time; capture burst concurrency, table size, and rows scanned. Avoid attributing public landing latency to the database.
2. If only the after-idle database query is slow, compare Neon's current plan with paid always-on compute (paid plans can disable scale-to-zero); verify cost against actual CU hours before changing architecture. If warm sequential DB round trips or connections dominate, prototype `PrismaPg` + **cache-disabled** Hyperdrive against Neon's direct endpoint on a nonproduction branch; keep migration CLI access direct and retain transaction/fresh-read tests. [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero); [Hyperdrive pricing](https://developers.cloudflare.com/hyperdrive/platform/pricing/); [Cloudflare Neon configuration](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/neon/).
3. Only revisit D1 if measured global read locality or cost justifies a substantial SQLite port. First spike schema conversion, Better Auth session correctness, outbox/lock atomicity, replica bookmarks, complete Postgres raw-SQL rewrites, data export/import and rollback, then load-test peak concurrency and D1 row metrics. Do not cut over on a 1,000-DAU projection alone. [Prisma v7 D1 workflow](https://www.prisma.io/docs/guides/v7/deployment/cloudflare-d1); [D1 observability and pricing](https://developers.cloudflare.com/d1/platform/pricing/).
