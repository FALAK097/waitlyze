# Hyperdrive for Waitlyze's Neon database

Researched 2026-11-11 against current Cloudflare and Neon documentation and installed package source. **Recommendation: keep the current Worker-to-Neon pooled path; do not add Hyperdrive now.** Revisit only if measured production latency or connection pressure warrants a driver migration.

## Current path

- `src/lib/prisma.js` constructs `PrismaNeon` with `@neondatabase/serverless`, `max: 1`, and a Neon `-pooler` hostname (rewritten when needed). Installed `@prisma/adapter-neon@7.10.0` constructs a `neon.Pool`, so this path uses Neon's **WebSocket** transport, not the HTTP `neon()` query function or ordinary Postgres TCP. [Neon driver docs](https://neon.com/docs/serverless/serverless-driver) and [installed adapter source](../node_modules/@prisma/adapter-neon/dist/index.mjs).
- `wrangler.jsonc` targets `aws:ap-southeast-1`, and the Neon CLI confirms Waitlyze’s primary compute is also in `aws-ap-southeast-1`. Cloudflare says placement near a database is especially useful for multiple sequential queries; the largest Hyperdrive benefit from eliminating **distant** connection handshakes is correspondingly less compelling here. This is a workload inference, not a measured latency claim. [Cloudflare placement](https://developers.cloudflare.com/workers/configuration/placement/) and [Hyperdrive architecture](https://developers.cloudflare.com/hyperdrive/concepts/how-hyperdrive-works/).
- Neon's `-pooler` endpoint already uses PgBouncer transaction pooling, designed for serverless connections. It solves the database connection fan-out problem that Hyperdrive also addresses, though it does not provide Hyperdrive's edge connection setup or query cache. [Neon pooling](https://neon.com/docs/connect/connection-pooling).

## What adding Hyperdrive would mean

- Hyperdrive supports Neon and Prisma, but Cloudflare's **Neon-specific** guide says to use `pg` or Postgres.js **instead of the Neon serverless driver** with Hyperdrive. Its Prisma guide uses `@prisma/adapter-pg` with `env.HYPERDRIVE.connectionString`. Thus the present `PrismaNeon`/WebSocket path cannot simply point at a Hyperdrive URL; this is a runtime adapter and binding change. Cloudflare says to supply a **direct, non-pooled Neon endpoint** as Hyperdrive's origin, avoiding a second transaction pool. Keep a direct database URL for Prisma CLI/migrations as appropriate. [Cloudflare Neon guide](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/neon/), [Cloudflare Prisma guide](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/prisma-orm/), [Neon pooling](https://neon.com/docs/connect/connection-pooling).
- Hyperdrive can still help if frequent cold Worker connections or many remote round trips dominate response time: it handles connection setup near the Worker, reuses connections near Neon, and can cache eligible reads. It adds another network/database layer and a transaction pool. It cannot remove query execution time or the round trips for uncached, sequential SQL. [How Hyperdrive works](https://developers.cloudflare.com/hyperdrive/concepts/how-hyperdrive-works/) and [connection pooling](https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/).
- **Do not enable its default query cache for Waitlyze's general Prisma client.** It defaults to 60 seconds plus 15 seconds stale-while-revalidate and does not invalidate on writes. Authentication, permissions, billing, dashboard updates, and read-after-write flows need fresh reads. A future trial should start with caching disabled; add a separate cached client only for explicitly stale-tolerant reads. [Cloudflare query caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/).
- Neon Free suspends compute after **five minutes of inactivity**; read-only CLI checks found 17 compute starts and 16 suspends since November 10. This remains a cold-start cost Hyperdrive does not promise to eliminate. Cloudflare documents Hyperdrive origin connections with a **10-minute idle timeout**, but neither vendor document establishes whether these idle connections prevent Neon suspension in this combination. Check Neon's compute status and active-time metrics in a trial; do not assume scale-to-zero savings or wake latency remain identical. [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero), [Hyperdrive limits](https://developers.cloudflare.com/hyperdrive/platform/limits/).
- Current Cloudflare pricing includes Hyperdrive on **Free and Paid Workers** plans (Free: 100,000 queries/day; Paid: unlimited, included), with roughly 20/100 maximum origin connections per configuration respectively. Neon's Hyperdrive guide still says Workers Paid is required; Cloudflare's current product pricing and limits are the controlling sources for Cloudflare plan availability. [Cloudflare pricing](https://developers.cloudflare.com/hyperdrive/platform/pricing/), [Cloudflare limits](https://developers.cloudflare.com/hyperdrive/platform/limits/), [Neon guide](https://neon.com/docs/guides/cloudflare-hyperdrive).

## Decision threshold

Keep PrismaNeon and Neon's pooled Singapore endpoint. If production traces show database connection setup or connection exhaustion as a material bottleneck, compare the current path against a **cache-disabled** `PrismaPg` + Hyperdrive prototype using the direct Neon endpoint. Measure warm and after-idle p50/p95 request and query latency, connection counts, and Neon active time, while exercising transactions and fresh reads. Adopt only if that measured gain exceeds the added adapter/configuration complexity and scale-to-zero behavior is acceptable. [Cloudflare Prisma example](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/prisma-orm/) and [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero).
